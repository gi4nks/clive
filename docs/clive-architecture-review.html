Staff architecture review · 18 October 2026

Clive

A macOS dual-pane file manager built with Tauri 2, Rust, React and TypeScript.

Largest strength
Filesystem authority and safety checks live in Rust, while the UI consumes focused native commands.

Largest flaw
The app shell concentrates too much navigation and workflow state; Rust filesystem capabilities also span broad concerns.

Module · bounded responsibility Deep Module · high leverage behind a small interface Leakage · details cross a Seam Seam · replaceable dependency boundary

Current Posture

Clive has a sound desktop architecture: React owns presentation and interaction; Rust owns filesystem effects, volume handling, trash, archive extraction, and the durable undo journal; Tauri commands form the native boundary. AI is optional and provider access is isolated behind a local gateway. OpenSpec specifications give behavior a canonical home. The current direction favors safety and explicit review over broad automation.

Candidates / Opportunities for Deepening

These are bounded changes that reduce observed Leakage. They are not a proposal to rewrite the app.

1. Unify AI proposal mutations behind one Rust journal

Implemented · P0 delivered

Evidence: Chat, quick actions, and plan review now call api.ts → commands/plan.rs (apply_plan/undo_plan). The duplicate frontend executor and direct write_text_file command have been removed from the AI path. Rust persists inverses under ~/.clive/plan-journal, checks mounted-volume identity, and now journals createFile using exclusive creation plus a SHA-256 checked inverse.

Problem: Before this change, shared proposal orchestration still executed common file operations through TypeScript adapters and handled file creation/trash outside the durable Rust journal. That left undo semantics split across languages.

Solution: The shared proposal controller normalizes operations and submits one batch through the Tauri Seam. Proposal creation and risk-specific review remain UI responsibilities; validation, path guards, execution order, journaling, progress, and undo remain Rust responsibilities.

Interface: batch identity, typed operations, progress, structured outcome, and durable undo reference. Implementation: Rust validation, mount checks, operation ordering, journaling, retryable partial undo, and content-checked generated-file removal. Seam: Tauri command API. Leverage: one execution policy for chat, quick actions, and plans. Tests: 384 frontend tests and 51 Rust tests pass, including content-preserving file undo. Locality: execution policy sits with filesystem authority.

2. Split the app shell by workflow ownership

Delivered · P1

Evidence: frontend/src/App.tsx was 1,966 lines at review time and remains a large shell. It composes pane navigation and sizing, selection, transfers, modal state, settings, previews, chat, AI planning, activity/debug views, and plan undo. It imports both low-level filesystem commands and many feature surfaces.

Problem: The app shell is an orchestration module with too many reasons to change. Adding a file workflow can couple layout, focus state, error messaging, and AI state. The shell is not a Deep Module because its interface is large and its implementation details are visible throughout.

Solution: Delivered workflow ownership in usePaneNavigation (path transitions and per-pane history), useTransferWorkflow (clipboard state, copy/cut/paste, batch transfers, pane refresh, swapping, and drag/drop), and usePreviewLayout (expanded preview mode and pane activation transitions). AI coordination already uses dedicated hooks. App.tsx supplies filesystem listing, write authorization, status, and UI callbacks, and composes the workflows. Context-menu construction, keyboard dispatch, and dialogs remain shell-owned UI composition.

Interface: workflow state plus explicit commands/events. Implementation: local transitions and side effects. Seam: composed React controller props/hooks. Leverage: change a workflow without editing the full shell. Tests: workflow tests avoid bootstrapping the whole app. Locality: related state, effects, and UI live together.

3. Give filesystem capabilities smaller Rust modules

Delivered · P1 · Locality

Evidence: at review time, src-tauri/src/commands/filesystem.rs spanned 1,501 lines and combined Finder tags/xattrs, native icons, path protection, listing, metadata, mount identity, transfers, volumes, Quick Look, and terminal launch. The Tauri command list remains registered centrally in main.rs.

Problem: Several platform capabilities shared a file and broad helpers, making safety changes difficult to localize and macOS behavior hard to isolate.

Solution: Delivered capability modules for path_safety, finder_tags, listing, metadata, macos, transfers, preview, desktop, tags, and volumes. filesystem.rs is now the namespace and shared safety-test home. Tauri command registration points directly to command implementations; Rust callers import the capability they use.

Interface: capability functions over paths and typed outcomes. Implementation: OS calls and safety policy remain in Rust. Seam: Tauri adapters are registered directly from each capability; path and mount guards remain explicit shared helpers. Tradeoff: more module files and explicit imports in exchange for locality; no new abstraction layer or runtime behavior. Tests: the unchanged guard, preview, volume, plan, trash, and archive coverage passes: 51 Rust tests.

4. Make the Tauri boundary a checked contract

Delivered · P1 · Seam

Evidence: all 43 commands were registered in main.rs, while frontend/src/api.ts separately maintained command names, payloads, and result types. The provider settings DTO also declared device in TypeScript while Rust returned untyped JSON without that field.

Solution: TauriCommandMap now types every wrapper. scripts/check-tauri-contract.mjs compares the map with generate_handler!, Rust command parameters and return types, and the fields of DTOs used by command results. The frontend build and tests run this check. Provider settings and build metadata now use serializable Rust DTOs; command rejections share a stable code/command/message error shape while preserving the original message.

Tradeoffs: the map is maintained in TypeScript rather than generated, so the checker protects command names, argument keys, return type names, and required DTO fields. Additive Rust DTO fields remain allowed for wire compatibility and journal metadata. UI presentation types stay in the frontend. Tests: contract checker plus wrapper tests; Rust and frontend suites run in validation.

5. Consider a first-class file search workflow

Explored · Speculative · P2

Evidence: File panes expose a local query/filter and Clive has a quick launcher, tags, and Finder reveal. The inspected command surface has no recursive search or content-index service. This is a product opportunity inferred from current capabilities, not a documented commitment.

Problem: Browsing remains directory-centric; discovering a file outside current pane contents requires navigation or Finder. Any recursive scan added directly to the UI would risk blocking and inconsistent permission/error handling.

Solution: Keep the current status-bar query as an in-pane name filter. Add a separate Search Files mode backed by a native, on-demand traversal. It accepts explicit roots, streams batches, supports cancellation, and reports whether the result set is partial. Do not introduce a persistent index in the first slice.

Interface: start(query, roots, options) → search ID; result batches and terminal status carry that ID; cancel(search ID). Implementation: Rust owns traversal and policy; React owns query, scope, progress, and result presentation. Seam: typed Tauri commands plus typed search events, following the existing plan-progress pattern. Leverage: bounded discovery can later support saved scopes without coupling traversal to panes. Tests: deterministic traversal, limits, mount loss, and cancellation. Locality: keep search rules in a dedicated Rust capability and the search view in its own frontend workflow.

Exploration decision record · proposed first slice

DR-SEARCH-01 · Recommend an ephemeral filename scan. This is a design recommendation, not an approved implementation commitment. Launch a dedicated Search Files mode (⌘⇧F); default its root to the active pane's current directory. Let the user add roots from Home, pinned folders, or mounted volumes. Show root chips so the active scope stays visible. Keep content indexing and saved searches out of this slice.

Initial traversal policy
  • Case-insensitive substring matching on file and folder names only.
  • Do not follow symbolic links; skip hidden entries by default, with an explicit include-hidden option.
  • Reject protected system roots; validate volume roots are mounted and stop when their mount identity changes.
  • Bound depth, visited entries, elapsed time, and returned results. Suggested starting caps: depth 12, 10,000 visited entries, 5 seconds, 500 results.
  • Report truncation/timeout as partial results with the reason; never present a partial scan as complete.
Failure and interaction policy
  • Unreadable folders are skipped and counted; root errors are shown to the user.
  • Cancel on Escape, closing Search Files, or replacing the active query; each result event is scoped by search ID.
  • Opening a result navigates the active pane to its parent and selects it; preview and Finder reveal use existing actions.
  • Keep results in memory only. A future index must be a separately reviewed product decision with storage, refresh, and privacy rules.
Option A · synchronous invoke

Smallest command surface, but the UI sees no intermediate results and cannot reliably interrupt a long network-volume scan. Poor fit for the stated cancellation requirement.

Option B · job + event batches

Recommended. A Rust worker traverses off the UI thread; start/cancel commands and ID-scoped result/status events provide responsive streaming and bounded lifecycle ownership.

Option C · persistent index

Fast repeated queries, but adds database lifecycle, stale-result handling, filesystem watchers/permissions, exclusions, and privacy expectations before Clive has validated demand.

Limits and product tradeoff: fixed caps make resource use predictable but can miss deeper or later results. The UI must show visited/result counts and why traversal stopped, offer “Search deeper” as a follow-up scope expansion, and preserve the completed partial results. Caps should be tuned from local-folder and SMB measurements before release. A name-only first slice does not replace Finder content search.

Evidence: frontend/src/widgets.tsx:117-146 exposes the existing query field; frontend/src/App.tsx:523-541 filters only the already-loaded entries by name per pane. src-tauri/src/commands/filesystem/listing.rs:19-64 lists one directory, excluding hidden entries by default. Commands are registered in src-tauri/src/main.rs:57-100; the typed frontend map is frontend/src/api.ts:51-95, with event subscription for plan-progress at lines 210-218. No recursive search, index, or search specification exists in the inspected command/spec surface.

Implementation boundary if approved: add a dedicated Rust search capability, command DTOs and registrations, typed command/event wrappers, and a frontend search workflow. Keep traversal policy independent from current pane filters. Existing Tauri event permissions already allow listen/unlisten through capabilities/default.json. The checked Tauri contract currently covers registered command names, arguments, Rust signatures, and DTOs; event names and payloads would need their own checked contract.

Ready for...

Daily local file management with a dual-pane workflow, preview, Finder tags, mounted-volume awareness, and reviewed/undoable batch organization. The Rust command layer is a strong base for safety-sensitive desktop work.

Still requires integration...

A single mutation and recovery path for every proposal origin, checked cross-language Tauri contracts, clearer workflow ownership in the app shell, and optional recursive search if cross-folder discovery is a core use case. These are recommendations, not claims that features are already implemented.
