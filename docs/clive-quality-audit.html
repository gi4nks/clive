Test infrastructure and safety

  • Rust unit tests use Cargo; frontend tests use Vitest, V8 coverage, Testing Library and jsdom. Frontend tests colocate as *.test.ts(x).
  • Filesystem-focused tests use temporary directories and disposable files. Failure injection exercises partial copy/move and undo branches without destructive access to user data.
  • Frontend setup mocks native invoke. Contract validation checks registered command names, signatures and DTO parity, but does not execute commands through a real WebView.
  • No automated end-to-end suite was identified. M5 manually launched the macOS bundle and verified one real directory-list IPC call.
  • Rust coverage uses LLVM tools on macOS and needs llvm-tools-preview; frontend coverage is V8. Rust branch coverage is not emitted by the current setup.
EvidenceSee Cargo.toml, tauri.conf.json, Tauri registration, frontend IPC API, Makefile, canonical Gitea workflow, and detailed measured coverage.

Acceptance criteria for each milestone

  • All filesystem mutations use fresh temporary directories and cleanup; no user paths or mounted home folders.
  • Every destructive workflow asserts both filesystem state and journal/recovery state for success and failure paths.
  • Relevant focused suite and make quality pass; diff review shows no unjustified coverage exclusions.
  • Record per-module line/branch/function results, runtime duration, failed/skipped counts, and any platform-only steps.
  • Raise aggregate line gates progressively (85% → 87% → 90%) only after the measured baseline consistently clears the proposed threshold.

Recommended release checklist

  1. Start from a clean, reviewed source snapshot; verify source manifests, changelog and tag all agree.
  2. Run make quality, make build, make verify-dmg and a macOS launch + representative IPC smoke.
  3. Record artifact SHA-256, architecture, macOS minimum version, commit SHA, ad-hoc signature and notarization status.
  4. Attach DMG, checksum and concise release notes to a GitHub Release if the mirror publishing process is approved and tested.
  5. Show the exact first-launch Gatekeeper steps; never instruct users to disable Gatekeeper globally.
  6. Keep a rollback path to the previous artifact and document known issues per version.
Trade-offWithout an Apple Developer Account, ad-hoc-signed Developer Preview distribution is possible but retains first-launch friction and no notarization reputation. Architecture opportunities and trade-offs

The capability-module split and typed Tauri boundary are meaningful improvements. The most valuable next architectural work is selective: make native effects injectable at the OS boundary and keep filesystem recovery behavior cohesive.

Transfer journal and rollbackDeep Module · LocalityTransfer implementation handles cross-device fallback, partial cleanup and undo. Keeping the journal/recovery invariant near the mutation flow makes the hardest behavior easier to reason about; too many wrappers could obscure the file operation.Preserve one cohesive transfer API; add explicit outcome types and state-invariant tests only where current error values lose recovery state.

Avoid a generic platform framework.
